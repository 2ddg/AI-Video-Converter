## 1. 需求理解与评审约束

原始需求 7 条，其中第 6 条是硬性筛选标准：**"审核会优先看你的界面选型，如果你的选型跟'客户端'关联为 0 不会考虑"**。

这条约束直接决定了选型方向：
- 纯 Web 网页版（浏览器里跑）→ 与"客户端"关联为 0 → 直接淘汰
- 桌面客户端（Electron / Tauri / PyQt 等）→ 命中"客户端"

因此本项目**首要目标不是功能多，而是必须是一个真正的桌面客户端**：原生窗口、任务栏图标、系统通知、本地文件操作、拖拽上传——这些"客户端特征"要在评审一打开应用就肉眼可见。

第 7 条"项目设计目标是给人用，不要做的东西自己都用不明白甚至都不测试"→ 要求**自测**，不能交一个跑不起来的空壳。本项目用 e2e 集成测试验证了 probe→缩略图→转换→进度→完成的全链路（见第 6 节）。

## 2. 技术选型决策

### 2.1 决策表

| 决策点 | 候选 | 选定 | 理由 |
|---|---|---|---|
| 客户端框架 | Electron / Tauri / PyQt / 纯 Web | **Electron** | 评审要求"客户端"强关联；本机**无 Rust 工具链**（已确认），Tauri 需装 Rust 全家桶，3 天风险极高；Electron + Node `child_process` 调 ffmpeg 是最顺路径；还能用 `shell.showItemInFolder`、系统 Notification 等原生能力强化"客户端感" |
| 构建工具 | 手写 vite+electron 串联 / electron-vite | **electron-vite 6** | 一份配置管 main/preload/renderer 三构建目标；`dev` 一条命令完成「起 vite 服务→等就绪→拉起 electron→main 改动自动重启」；自动 externalize node/electron 内建模块；产出 `out/` 直接被 electron-builder 消费。手写方案要在 dev 脚本里做端口轮询、main 重启编排，是 Windows 上最容易翻车的部分 |
| 渲染框架 | Vue 3 / React / 原生 | **Vue 3.5 `<script setup>` + TS + Pinia** | 生态熟、开发效率高；Pinia 管 video/tasks/settings 三个 store |
| 路由 | vue-router / 单页 | **单页** | 减一个依赖；单页 HomeView 足够承载上传→信息→转换→队列全流程 |
| 样式 | 组件库(Element/Naive) / 手写 CSS | **手写 scoped CSS + 设计令牌** | 展示功底、零依赖风险、评审一眼看懂；深色玻璃拟态手写完全可控 |
| 模块格式 | ESM / CJS | **主/预加载 CJS**（package.json 不设 type:module） | 规避 ESM 下 `__dirname`/打包兼容坑；electron-vite 自动处理 |
| ffmpeg 集成 | ffmpeg API(libavformat/libavcodec) / 命令行 | **命令行**（spawn ffmpeg.exe） | 需求第 2 条明确"可以用 ffmpeg 的命令行（不要求接入 ffmpeg api）"；命令行稳定、调试方便、零原生依赖 |

### 2.2 为什么不是 Tauri

Tauri 体积更小、更现代，但本项目环境**没有 Rust 工具链**（`where cargo` 无结果），安装 Rust + VS C++ 构建工具链在限时三天内有不可控风险。Electron 虽然体积大，但二进制可走 npmmirror 国内镜像加速，且 Node 生态与 ffmpeg CLI 集成最直接。**权衡后选 Electron，用"客户端特征截图"反证评审的"纯 Web 判 0 分"**。

## 3. 关键实现决策

### 3.1 无 ffprobe 的视频信息探测

环境里只有 `ffmpeg.exe`（无 `ffprobe.exe`）。决策：用 `ffmpeg -hide_banner -i <input>` 探测，信息在 **stderr**，退出码 1（"At least one output file must be specified"）但解析到数据即视为成功。

实测输出格式（以此为准设计正则）：
```
Duration: 00:00:15.00, start: 0.000000, bitrate: 1723 kb/s
Stream #0:0[0x1](und): Video: h264 (High), yuv420p, 1280x720, 1588 kb/s, 30 fps
Stream #0:1[0x2](und): Audio: aac (LC), 44100 Hz, mono, fltp, 127 kb/s
```

逐行扫描正则（比单条大正则稳）：
- `Duration:\s*(\d+):(\d+):(\d+(?:\.\d+)?)` → 时长
- `bitrate:\s*(\d+(?:\.\d+)?)\s*kb\/s`（首个命中行）→ 总码率
- `Video:\s*([\w-]+).*?(\d{2,5})x(\d{2,5}).*?,?\s*(\d+(?:\.\d+)?)\s*fps` → 视频 codec/宽/高/帧率
- `Audio:\s*([\w-]+)` → 音频 codec

兜底：`Duration: N/A` 时按 `sizeBytes / (bitrateKbps*1000/8)` 估算时长；探测 15s 超时 kill 防卡死。

### 3.2 转换进度解析（含一个 ffmpeg 知名坑）

用 `-progress pipe:1 -nostats` 输出机器可读键值对，主进程 `readline` 逐行解析：
```
frame=90 / fps=0.00 / out_time_us=2933333 / out_time_ms=2933333 / speed=8.05x / progress=continue|end
```

**坑：`out_time_ms` 的值实际是微秒**（与 `out_time_us` 相同，均为 2933333=3s），不是毫秒。这是 ffmpeg 长期未修的已知问题。本项目**以 `out_time_us` 为准**计算百分比：`percent = out_time_us/1e6 / durationSec × 100`。

进度推送节流 ≥100ms 防 IPC 洪泛；ETA = `(duration - outTime)/speed`；`progress=end` 强制 100%。

### 3.3 GPU 硬件编码检测（招牌优化）

**不能只看编译开关**：ffmpeg build 里编了 `h264_nvenc` 不等于机器有 N 卡。本项目用**运行时试编码探测**：对每个候选硬编（h264_nvenc / h264_amf / h264_qsv / hevc_*）跑一次零输入零落盘的试编码：
```
ffmpeg -f lavfi -i testsrc=duration=0.2:size=64x64:rate=5 -frames:v 1 -c:v {enc} -f null -
```
退出码 0 即真正可用，结果缓存到 settings.json（24h 有效）。检测到后在 UI 显示徽章"已启用 GPU 加速"，无 GPU 自动回落 libx264。

**自测结果**：本机（Intel 核显）检测到 `h264_qsv` 可用，徽章正确显示"Intel · H.264 QSV"。

### 3.4 Windows 中文路径规避

- 一律 `spawn(exe, args数组)`，**绝不 `exec` 字符串拼接**（CreateProcess 宽字符传参，中文/空格/`%` 全安全）
- `-nostdin`（防 ffmpeg 读 stdin 挂起）、`-y`（防"文件已存在"交互卡死）、`windowsHide: true`（防黑窗闪现）
- 输出默认写到输入同目录 `原名_converted.ext`，同名追加序号，不覆盖源文件

### 3.5 缩略图策略

取时长 10% 处截图避开黑屏片头/品牌 logo；`-ss` 前置（demuxer seek，快）；`scale=320:-2`（-2 保证偶数分辨率）；`-q:v 3` JPEG 质量。三帧预览（10%/50%/90%）供 hover 切换。

显示用自定义协议 `thumbnail://<hash>.jpg`（`protocol.handle` + `registerSchemesAsPrivileged`），校验 `startsWith(thumbDir)` 防路径穿越。

### 3.6 打包：ffmpeg 走 extraResources

`ffmpeg.exe` 绝不进 asar（打包后读不到），走 `electron-builder` 的 `extraResources` 复制到 `resources/ffmpeg/`，运行时主进程用 `process.resourcesPath` 定位。开发与打包共用 `resources/ffmpeg/` 路径策略，避免"开发能跑、打包后找不到 exe"的经典坑。

## 4. AI 协作记录（prompt → 产出 → 反馈 → 迭代）

### 4.1 ffmpeg 下载链路

- 初次尝试 `winget install Gyan.FFmpeg` → **失败**（`InternetOpenUrl() failed 0x80072efd`，GitHub 直连 89KB/s）
- 尝试 `gyan.dev` 直连 → **24KB/s，太慢**
- 改用 `pip download imageio-ffmpeg`（清华 PyPI 镜像，秒下）→ 解包 wheel 提取 `ffmpeg-win-x86_64-v7.1.exe`（87MB，ffmpeg 7.1 essentials）→ **成功**
- **决策反馈**：国内环境下载大文件优先走 PyPI/npm 国内镜像，不走 GitHub 直连

### 4.2 Electron 二进制下载

- `npm install` 完成，但 electron 二进制**未下载**：npm 11 的 `allow-scripts` 策略拦截了 electron 的 postinstall 脚本
- `npm approve-scripts electron` 批准 → 仍 `TypeError: fetch failed`（npm 11 不再把 `.npmrc` 的 `electron_mirror` 传给 install 脚本）
- **最终方案**：用环境变量 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/` 直接跑 `node node_modules/electron/install.js` → **成功下载 247MB electron.exe**
- **决策反馈**：`.npmrc` 的 `electron_mirror` 键在 npm 11 下已废弃（报 "Unknown project config"），改用环境变量

### 4.3 ELECTRON_RUN_AS_NODE 导致应用无法启动

- `npm run dev` 报 `TypeError: Cannot read properties of undefined (reading 'requestSingleInstanceLock')`
- 排查发现 `require('electron')` 返回的是**字符串路径**而非 API；`electron --version` 打印 `v24.22.0`（Node 版本）而非 Electron 版本
- 根因：环境变量 **`ELECTRON_RUN_AS_NODE=1`** 被设置，导致 electron 二进制以纯 Node 模式运行，内置模块 patch 失效
- 解决：启动前 `unset ELECTRON_RUN_AS_NODE` → `electron --version` 返回 `v44.8.0`，`require('electron').app` 正常返回对象
- **决策反馈**：Electron 应用启动失败时优先检查 `ELECTRON_RUN_AS_NODE` 环境变量

### 4.4 mkv 容器 muxer 名坑（e2e 测试发现）

- e2e 测试转 mkv 失败：`Requested output format 'mkv' is not known`
- 根因：`-f mkv` 中的 `mkv` 不是有效 muxer 名，mkv 对应的 muxer 名是 `matroska`
- 修复：从 buildArgs 移除 `-f {container}`，让 ffmpeg 依据输出文件扩展名（.mkv/.mp4/.webm/.mov/.avi/.gif）自动选 muxer
- **决策反馈**：e2e 测试价值巨大——这个 bug 手工点 UI 也可能撞到，但 e2e 让我在提交前就发现并修复了

### 4.5 GPU 检测方案演进

- 初版方案：静态读 `ffmpeg -encoders` 输出里有没有 `h264_nvenc` → **否决**：编译进 build ≠ 机器有对应 GPU
- 演进：运行时试编码（零输入零落盘）探测真实可用性 → **采纳**，并缓存结果

## 9. 收尾复核与修复（截图验收阶段）

### 发现的问题与根因

1. **02/03 截图字节完全相同**：截图脚本在页面顶部固定等待后截图，而任务队列在折叠线以下。转换实际成功，但画面里看不到进度。→ 脚本改为轮询任务状态，先滚动到任务卡，再在进度 ≥5% 与 done 时分别截图；截图前清空历史，画面只保留当前任务。
2. **视频信息第 4 列被裁切**：380px 左栏内 4 列 grid 的子项默认 `min-width: auto`，长编码值把列撑破。→ 改为 3 列 `minmax(0, 1fr)`，tile 加 `min-width: 0`，标签省略号。
3. **"开始转换"文字竖排**：按钮内 SVG 未设尺寸，默认内在宽度参与 flex 计算，按钮被压到最小内容宽度后中文逐字换行。→ SVG 固定 18px，按钮 `white-space: nowrap` + `flex-shrink: 0`，footer 允许换行。
4. **任务卡一直显示"排队中"**：进度事件只更新百分比，从未把状态从 `queued` 改为 `converting`。→ `applyProgress` 收到首个进度即置 `converting`，顶部"1 个转换中"同步正确。
5. **GPU 检测被一次失败锁死一天**：原逻辑把 `available: false` 也缓存 24h；一次瞬时失败后，即使 `h264_qsv` 实测可编码，界面仍显示软件编码。→ 仅缓存可用结果 24h，失败结果下次重试。
6. **自动切换硬编时误选 NVENC**：原逻辑取容器内第一个硬件编码器，未匹配实际探测结果。→ 只从 `gpu.encoders` 中选择；GPU 提示也只列真实可用的编码器。
7. **转换开始后看不到队列**：→ 表单提交成功后平滑滚动到任务队列。
8. **e2e 依赖 `D:/temp` 样例，换机不能跑**：脚本硬编码 `D:/temp/test_720p.mp4`，README 说自动生成但实际没有。→ 首次运行自动用内置 ffmpeg 生成 15s 720p 样例，输出改到系统临时目录；新增 `npm run test:e2e`（先 build 再跑）。
9. **进度结束事件回落到 0%**：`progress=end` 的空 block 被当作 0% 发出，e2e 最后采样为 0。→ 结束事件强制按总时长发 100% 并绕过节流，重复的结束 emit 删除；e2e 最后采样恢复 100。
10. **运行命令与 Windows 平台不一致**：README/总结用 `unset` 和 `./node_modules/.bin/electron`。→ 改 PowerShell 命令、`npm run test:e2e`，环境要求改为 Node 22.12+。

### 复测结果

- `npm run typecheck` 通过；`npm run test:e2e` 通过（内含 build）。
- `screenshot.js`：01 加载（Intel QSV 徽章 + 自动选中 H.264 QSV）、02 转换中（进度条 + 编码速度 + 剩余时间）、03 完成（输出路径 + 操作按钮），02/03 SHA256 不同。
- `e2e`：`ALL_OK: true`，GPU `available: true`（Intel h264_qsv），自动生成样例，输出 `.../video-converter-e2e/output/test_720p_converted.mkv` 真实存在；进度采样 24/62/100。

### 决策

- 截图必须是真实状态的证据，不用同一张图冒充两个状态；自动化脚本必须轮询真实任务状态。
- 检测类功能不缓存失败结果：宁可下次多花 1 秒，也不要把一次抖动放大成一天的错误结论。
- 自测脚本必须自包含：样例自动生成、输出写系统临时目录，不依赖开发机的 `D:/temp`。
- 面向 Windows 的交付文档必须给 PowerShell/CMD 命令，不能只写 Unix 命令。
